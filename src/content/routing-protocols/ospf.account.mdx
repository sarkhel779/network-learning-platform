<h2 id="inspect-ospf-evidence">Inspect OSPF evidence</h2>

`show ip ospf neighbor` is the first command to check: it lists every neighbor and its current state, and any state other than **Full** (or **2-Way** on a non-DR/BDR multi-access neighbor, which is expected) means the adjacency has not finished forming. `show ip ospf database` lists every LSA type the router holds, organized by area — a fast way to confirm whether two routers actually share an identical LSDB.

<h2 id="guided-ospf-cost-practice">Guided OSPF cost practice</h2>

With the default reference bandwidth of 100 Mbps, compute the total cost of a path crossing a 100 Mbps link, then a 1 Gbps link, then a 10 Mbps link: 100,000,000/100,000,000 = 1, plus 100,000,000/1,000,000,000 rounds up to 1, plus 100,000,000/10,000,000 = 10. Total cost = 1 + 1 + 10 = 12.

<h2 id="troubleshoot-ospf">Troubleshoot OSPF</h2>

1. Confirm both routers have OSPF enabled on the correct interfaces and agree on the area number for that link.
2. Check for a Hello or Dead interval mismatch — OSPF requires these to match exactly between neighbors on the same link.
3. Look for a duplicate Router ID on the network, which can prevent an adjacency from forming correctly or cause it to flap.
4. If a neighbor is stuck in ExStart or Exchange, suspect an MTU mismatch: routers that disagree on the largest DBD packet size can appear to negotiate but never finish exchanging LSA summaries.
5. Verify authentication settings match on both sides if OSPF authentication is configured.
6. On a multi-access network, confirm the DR/BDR election completed as expected — a router stuck below 2-Way with the DR usually means one of the checks above failed specifically toward the DR.
