<h2 id="inspect-bgp-evidence">Inspect BGP evidence</h2>

`show ip bgp summary` is the first command to check: it lists every configured neighbor and its current session state. Anything other than a number (the count of received prefixes) in the state column — Idle, Active, Connect, OpenSent, OpenConfirm — means the session has not reached Established, and no routes are being exchanged with that neighbor yet. `show ip bgp` (or `show ip bgp <prefix>`) lists the routes themselves along with their path attributes, so you can see exactly why the decision process picked the route it did.

<h2 id="guided-bgp-path-selection-practice">Guided BGP path-selection practice</h2>

Two routes reach the same prefix: Route A has LOCAL_PREF 200 and a 3-AS-long AS_PATH; Route B has LOCAL_PREF 100 and a 1-AS-long AS_PATH. Because LOCAL_PREF is compared before AS_PATH length in the decision process, Route A wins outright — its longer AS_PATH is never even considered.

<h2 id="troubleshoot-bgp">Troubleshoot BGP</h2>

1. Confirm basic IP reachability and that nothing is blocking TCP port 179 between the two routers.
2. Check for an AS number mismatch — each side must be configured with the AS number its peer expects, for both eBGP and iBGP.
3. If the session is stuck in Active or Idle, the TCP connection itself is failing; verify routing to the peer's address exists independently of BGP.
4. If the session reaches Established but a prefix does not appear, check outbound and inbound routing policy (prefix lists, route maps, distribute lists) on both sides before assuming a protocol fault.
5. Confirm the NEXT_HOP in a received route is actually reachable — an eBGP-learned NEXT_HOP that is not directly reachable, or not reachable via an IGP route in an iBGP scenario, will keep the route out of the forwarding table even though BGP accepted it.
6. When two routes both look valid but only one is used, read the path attributes directly with `show ip bgp <prefix>` and walk the decision process in order rather than guessing.
