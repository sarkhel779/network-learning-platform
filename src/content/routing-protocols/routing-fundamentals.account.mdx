<h2 id="inspect-routing-table-evidence">Inspect routing table evidence</h2>

On a representative network device, `show ip route` prints a legend before the route list — read it first. Each line's leading code (`C` for connected, `S` for static, `O` for OSPF, `D` for EIGRP, `R` for RIP, `B` for BGP) tells you the **source**, and therefore which administrative distance applied when this route was chosen. The bracketed pair after the prefix, such as `[110/64]`, is `[administrative distance/metric]` — the exact two numbers this lesson has been building toward. On Linux, `ip route show` lists the winning routes only; `ip route show table all` and per-protocol tools (`vtysh` on FRRouting, for example) are needed to see routes that lost the AD comparison and were never installed.

<h2 id="guided-metric-calculation-practice">Guided metric-calculation practice</h2>

Work this by hand before checking the answer. A path crosses two links: a 100 Mbps link and a 10 Mbps link.

For **OSPF** (reference bandwidth 100 Mbps): cost = 100,000,000 ÷ 100,000,000 = 1 for the first link, and 100,000,000 ÷ 10,000,000 = 10 for the second link. Total path cost = 1 + 10 = **11**.

For **EIGRP** (default K-values, so Metric = 256 × (BW + Delay)): the bandwidth term uses the *minimum* bandwidth on the path, not the sum — so BW term = 10,000,000 ÷ 10,000 kbps = 1,000, using the slower 10 Mbps link. Delay is cumulative across both links, not just the slowest one.

<h2 id="troubleshoot-routing-selection">Troubleshoot routing selection</h2>

1. Identify every source currently advertising the destination prefix (`show ip route <prefix>` or the equivalent protocol-specific command, e.g. `show ip ospf database`, `show ip eigrp topology`).
2. Confirm which source actually won by reading the installed route's `[AD/metric]` pair, not by assuming which protocol "should" win.
3. If the installed source is a surprise, compare its administrative distance against every other candidate source first — a lower-AD source anywhere overrides a better metric everywhere else.
4. Only if two candidates share the same source and the same administrative distance, compare their metrics using that protocol's own formula.
5. Check for a static route with an unexpectedly low administrative distance (including a floating static route intentionally configured with a higher AD as a backup) before assuming a dynamic protocol misbehaved.
6. Confirm the metric components themselves are correct at the source — a misconfigured interface bandwidth or delay value produces a mathematically correct but practically wrong EIGRP or OSPF metric.
