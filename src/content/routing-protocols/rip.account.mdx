<h2 id="inspect-rip-evidence">Inspect RIP evidence</h2>

On a representative network device, `show ip protocols` confirms RIP is running, which interfaces are participating, and the configured timers. `show ip rip database` (or the equivalent RIP topology command) lists every route RIP has learned, including ones a lower-administrative-distance source has kept out of the actual routing table.

<h2 id="guided-rip-convergence-practice">Guided RIP convergence practice</h2>

Work through "counting to infinity" by hand: three routers in a line, A–B–C, all know about a network attached to A with metrics 1 (at B) and 2 (at C). A's link to that network fails. Without split horizon, B might momentarily still hear C's old, now-stale route (metric 2) and re-advertise it as metric 3, C then re-advertises 4, and so on — climbing toward infinity instead of converging immediately.

<h2 id="troubleshoot-rip">Troubleshoot RIP</h2>

1. Confirm RIP is enabled on the correct interfaces with `show ip protocols`, and that the network statements cover the intended subnets.
2. Verify RIPv2 is in use, not RIPv1, if VLSM or discontiguous subnets are in play — RIPv1 cannot carry a subnet mask.
3. Check for a mismatched RIP version or missing multicast/broadcast reachability between neighbors (RIPv1 broadcasts, RIPv2 multicasts to 224.0.0.9 by default).
4. Inspect the RIP database for routes stuck at metric 16 — that is a poisoned, not a missing, route, and points at a real reachability change.
5. Confirm passive-interface configuration is not silently suppressing updates on an interface that should be participating.
6. If routes flap, check whether split horizon has been disabled on a hub-and-spoke or NBMA-style topology, which is one of the few cases where doing so is intentional — and risky.
