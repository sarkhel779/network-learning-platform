<h2 id="inspect-eigrp-evidence">Inspect EIGRP evidence</h2>

`show ip eigrp neighbors` lists every EIGRP neighbor along with the Hold time and uptime — a neighbor that keeps resetting its uptime is dropping and reforming, not staying stable. `show ip eigrp topology` shows every path EIGRP knows for each destination, not just the installed one: entries marked as the successor and any feasible successors are visible here, along with their Feasible Distance and Reported Distance.

<h2 id="guided-eigrp-metric-practice">Guided EIGRP metric practice</h2>

With default K-values, compute the composite metric for a path with a 1,000,000 kbps (1 Gbps) minimum bandwidth and a cumulative delay of 100 (tens of microseconds): `BW term = 10,000,000 / 1,000,000 = 10`. `Metric = 256 × (10 + 100) = 28,160`.

<h2 id="troubleshoot-eigrp">Troubleshoot EIGRP</h2>

1. Confirm both routers are configured with the same Autonomous System number — EIGRP neighbors will not form across mismatched AS numbers.
2. Check for a K-value mismatch: routers must agree on which K-values are enabled, or the neighbor relationship will not come up at all.
3. Verify Hello and Hold timers are compatible, and that no access list or firewall rule is silently dropping EIGRP's IP protocol 88 traffic.
4. In `show ip eigrp topology`, distinguish a missing feasible successor (no backup exists, so a failure forces a Query) from a stable feasible successor already in place.
5. If a route stays Active for an extended period, suspect a **Stuck-In-Active (SIA)** condition: a neighbor never replied to a Query, often because that neighbor is overloaded or the query propagated too far across a large network.
6. Check interface bandwidth and delay configuration for accuracy — a misconfigured value produces a mathematically valid but practically wrong composite metric, same as with OSPF cost.
