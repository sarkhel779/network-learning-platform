<h2 id="inspect-neighbour-evidence" tabIndex={-1}>Inspect neighbour evidence</h2>

<a className="primary-link" href="#troubleshoot-arp-methodically">I know this—proceed to advanced</a>

Use the operating system's neighbour table and a capture together. A cache entry reports local state;
it does not prove that the application works or that the mapping is legitimate.

- Windows legacy view: `arp -a`
- Windows PowerShell: `Get-NetNeighbor -AddressFamily IPv4`
- Linux: `ip neigh show`

Common states include reachable/validated, stale, probe or delay transitions, and incomplete/failed.
Names and timers vary by operating system, so interpret the state with recent traffic and capture evidence.

<h2 id="troubleshoot-arp-methodically">Troubleshoot ARP methodically</h2>

1. Record the source address, prefix, destination and selected route.
2. Decide whether the intended next hop is the destination or a gateway.
3. Inspect the relevant neighbour entry without clearing unrelated evidence.
4. Capture on the correct local interface and verify the request leaves.
5. Confirm the switch floods within the correct VLAN and excludes ingress.
6. Check whether an owner or configured proxy replies with the expected mapping.
7. Compare the reply with the cache and then test the original traffic in both directions.

If no request appears, investigate route selection, interface state and an already-usable cache entry.
If requests appear without replies, verify VLAN membership, target availability, duplicate addressing,
host filtering and whether the target IP is actually local. Repeated incomplete entries show failed
resolution; they do not by themselves identify which device or link caused the failure.

Proxy ARP deserves special suspicion when an incorrectly masked host still reaches another subnet.
Compare the host's prefix and intended gateway with the router's proxy configuration before accepting
reachability as proof that addressing is correct.

<InterviewScenario prompt="A host can reach a remote server, but its neighbour table contains only the gateway and not the server. Is that a fault?">
No. The IP destination is remote, so the host resolves only the local next hop—the gateway. The router
uses separate Layer 2 delivery on later links. Confirm the route, gateway mapping and packet's unchanged
remote IP destination rather than expecting a remote-server MAC in the local cache.
</InterviewScenario>

<InterviewScenario prompt="Two devices report the same IPv4 address after a failover. What ARP evidence would you collect?">
Capture gratuitous announcements and ordinary requests/replies, compare sender MACs and timing, inspect
neighbour-cache changes, and identify the intended owner. A failover announcement can legitimately
refresh a shared address, while alternating or conflicting replies may indicate duplicate ownership.
</InterviewScenario>
