<h2 id="inspect-routing-evidence">Inspect routing evidence</h2>

On **Windows**, compare `route print` with `Get-NetRoute`; verify the address family, destination prefix, next hop, interface index, and metric. On **Linux**, use `ip route` for IPv4 and `ip -6 route` for IPv6. On a representative network device, use commands such as `show ip route` and `show ipv6 route`, then inspect the legend before interpreting route-source codes.

Capture traffic in **Wireshark** while testing a known path. Confirm that the IP destination remains the final endpoint while Ethernet source and destination addresses change at each routed link. A reduced IPv4 TTL or IPv6 Hop Limit is forwarding evidence. ICMP or ICMPv6 errors are useful evidence when present, but their absence is not proof that no router discarded the packet.

<h2 id="guided-routing-practice">Guided routing practice</h2>

For each destination, write the candidates in this order: correct address family, matching prefixes, longest prefix, lowest administrative distance among equal prefixes, and lowest comparable metric if a genuine tie remains. Then state the outgoing interface, next hop, expected Layer 2 target, and whether TTL or Hop Limit permits forwarding.

<h2 id="troubleshoot-routing">Troubleshoot routing methodically</h2>

1. Confirm the destination address and whether the packet is IPv4 or IPv6.
2. Verify that at least one prefix matches, including a usable default if required.
3. Apply longest-prefix match before comparing route sources.
4. For equal prefixes, check administrative distance; compare metrics only when they are genuinely comparable.
5. Verify the selected outgoing interface is operational and the next hop is reachable on that link.
6. Inspect ARP or NDP evidence for next-hop Layer 2 resolution.
7. Check TTL or Hop Limit and identify the router responsible for any discard.
8. Correlate packet evidence with conditional ICMP or ICMPv6 messages and filtering policy.
