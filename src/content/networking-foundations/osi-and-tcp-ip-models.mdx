# OSI and TCP/IP Models

Layered models help teams describe one browser-to-server exchange without treating it as one
undifferentiated event. The browser creates a request, transport selects a conversation, IP
identifies an end-to-end path, and local networking carries each frame as signals. This lesson
uses the models as practical reasoning tools, not as a claim that every implementation fits
perfectly into fixed boxes.

<h2 id="why-layers">Why layered models exist</h2>

Layering separates responsibilities. A laptop can move from Ethernet to Wi-Fi while its browser
still uses the same HTTP request and destination IP address. When something fails, the layers
give us an ordered way to ask what is working: the link, local delivery, the IP path, transport,
or the application.

The models are useful when they lead to a specific question: *which information is a protocol or
device using to make its decision?* They are not a memorization test or a promise that real
software always divides itself in the same way.

<h2 id="osi-model">The seven OSI layers</h2>

The **Open Systems Interconnection (OSI)** model names seven conceptual layers. Read downward
while the sender prepares data, then upward while the receiver uses it.

| OSI layer | Browser-to-server example | Main question |
| --- | --- | --- |
| Application | HTTP, DNS, DHCP | What service or data does the application need? |
| Presentation | Representation, compression, encryption formats | How is the application data represented? |
| Session | Organizing an application exchange | How is the application interaction managed? |
| Transport | TCP, UDP, and ports | Which application conversation receives the data? |
| Network | IPv4 and routing | Which network path leads toward the destination? |
| Data Link | Ethernet, Wi-Fi, MAC addresses, frames | Which local device receives this frame? |
| Physical | Copper, fiber, radio, bits | How are bits signaled across this medium? |

Modern applications often handle the top three responsibilities together. That grouping helps
explain why the TCP/IP model has fewer layers.

<h2 id="tcp-ip-model">The four-layer TCP/IP model</h2>

The **TCP/IP** model describes the Internet protocol suite in four layers:

- **Application:** services such as HTTP, DNS, and DHCP.
- **Transport:** TCP or UDP plus ports, which identify a host conversation.
- **Internet:** IP addresses and routing between networks.
- **Network Access:** Ethernet or Wi-Fi frames, MAC addresses, and the physical medium.

TCP is a transport protocol, not the name of the entire model. A UDP exchange can use the same
Internet and Network Access layers while making a different transport choice.

does not deliver the browser's HTTP request to its own application.

<h2 id="device-layer-scope">What each network device examines</h2>

No device is permanently limited to one layer. This comparison describes what each device
**commonly examines** in a familiar network task.

| Device | Commonly examines | Practical scope |
| --- | --- | --- |
| Host or server | Application through Physical | Creates or consumes application data and uses a network interface. |
| Layer 2 switch | Physical and Data Link / Network Access | Uses local-link information, commonly a destination MAC address, to forward a frame. |
| Router | Physical, Data Link, Network / Internet | Receives a frame, routes with the destination IP, then builds an outgoing frame. |
| Firewall | Packet, transport, sometimes application information | Scope depends on design; it can be application-aware without this lesson teaching policy configuration. |

One home gateway can contain an access point, switch, router, and firewall. The functions stay
distinct even when they share hardware.

<h2 id="wireshark-layers">Wireshark layer identification</h2>

Capture on the active host interface and choose a filter that matches your question.

| Filter | Evidence to identify |
| --- | --- |
| `eth` | Ethernet frames and local-link addresses |
| `ip` | IPv4 source and destination |
| `tcp` | TCP ports and conversation details |
| `udp` | UDP datagrams and ports |
| `dns` | Application request and response names |
| `http` | HTTP methods, status codes, and headers when visible |
| `tls` | Encrypted web-traffic records and handshake evidence |

points only when you have access to them.

<h2 id="troubleshooting-interview">Troubleshooting and interview scenarios</h2>

Work upward from link, to local delivery, to IP path, transport reachability, and application
behavior. A successful lower-layer check narrows the next question; it does not prove every
higher layer is healthy.

<InterviewScenario prompt="A laptop has a link light but cannot open an internal website. How would you organize your first checks?">
  Verify the interface and link, then check local addressing and gateway reachability. Next test
  the IP path toward the server, determine whether the needed TCP or UDP transport is reachable,
  and finally inspect the application response. Explain the evidence at each layer rather than
  treating a link light as proof that HTTP is healthy.
</InterviewScenario>

<InterviewScenario prompt="How would you explain encapsulation and compare OSI with TCP/IP in an interview?">
  Describe a browser request gaining transport, IP, and local-frame information at the sender,
  then losing it in reverse at the receiver. Explain that OSI separates seven conceptual layers
  while TCP/IP groups them into four practical layers. Anchor the answer to HTTP, TCP or UDP,
  IPv4, and Ethernet or Wi-Fi instead of reciting layer names alone.
</InterviewScenario>
