<h2 id="eigrp-basics">EIGRP basics</h2>

**EIGRP** (Enhanced Interior Gateway Routing Protocol) is a Cisco-originated protocol, later published as an informational standard, that behaves like an advanced distance-vector protocol: it exchanges routes with neighbors much like RIP, but uses the **DUAL** (Diffusing Update Algorithm) to guarantee loop-free paths and near link-state convergence speed without flooding a full topology map. Its composite metric can weigh bandwidth, delay, load, and reliability, and it supports **unequal-cost load balancing**, which pure shortest-path protocols do not. Because it originated as a single-vendor protocol, EIGRP interoperability outside Cisco-heavy environments is limited.

<h2 id="inspect-routing-protocol-evidence">Inspect routing protocol evidence</h2>

On a representative network device, `show ip protocols` lists which routing protocols are configured and their timers, and `show ip route` shows which routes were learned by which protocol from the route-source code in the left column. For OSPF specifically, `show ip ospf neighbor` confirms whether an adjacency reached the `FULL` state, and `show ip ospf database` shows the link-state database each router is computing from. For BGP, `show ip bgp summary` shows each peer's session state, where `Established` means the session is up and exchanging routes, and how many prefixes were received.

Capture control-plane traffic in **Wireshark** to see the protocols themselves: OSPF Hello packets negotiate and maintain adjacencies on a fixed interval, and a BGP OPEN message begins a peering session before UPDATE messages carry actual route advertisements and withdrawals.

<h2 id="troubleshoot-routing-protocols">Troubleshoot routing protocols methodically</h2>

1. Confirm the protocol is actually running and enabled on the relevant interfaces with `show ip protocols` or the OSPF, BGP, or EIGRP equivalent.
2. For OSPF or EIGRP, verify neighbor adjacencies formed; a stuck state usually points at mismatched timers, area IDs, authentication, or an MTU mismatch.
3. For BGP, verify the peer session reached `Established`; a session stuck in `Idle` or `Active` usually means a reachability, TCP port 179, or authentication problem, not a routing-logic problem.
4. Compare the routing table's learned routes against what the protocol's own database or table, such as the link-state database, topology table, or BGP table, says should be reachable.
5. Check for route filtering, redistribution, or administrative distance differences suppressing an expected route.
6. Correlate with packet captures of the protocol's own control traffic to see whether advertisements are actually being sent and received.

<InterviewScenario title="The neighbor is up, but the route is missing">Two OSPF routers show a `FULL` adjacency, but a route from one is missing on the other. Separate a filtering problem from a metric or area-boundary problem, and name the commands you would use to tell them apart.</InterviewScenario>
