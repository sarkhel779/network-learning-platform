<h2 id="inspect-transport-evidence">Inspect transport evidence</h2>

Use Wireshark display filters `tcp` and `udp`. Narrow a TCP opening with `tcp.flags.syn == 1`; inspect possible recovery with `tcp.analysis.retransmission`, then confirm sequence ranges and acknowledgements yourself. On Linux, compare listeners and conversations with `ss -tulpen` or `netstat -an`. On Windows, use `Get-NetTCPConnection`, `Get-NetUDPEndpoint`, or `netstat -ano`, then map the process identifier to the expected application.

<WiresharkCheck displayFilter="tcp || udp">Capture one transport conversation. Record protocol, source and destination IP addresses and ports, TCP flags or UDP length, the matching listener, and the application evidence.</WiresharkCheck>

<h2 id="guided-transport-diagnosis">Guided transport diagnosis</h2>

Separate IP reachability from transport and application behavior. A returned RST is explicit TCP rejection evidence. Repeated SYN packets without a response show an incomplete attempt, but do not identify whether the request, response, policy, host, or return path caused the silence. A completed handshake proves transport establishment, not that the application returned correct data.

<h2 id="troubleshoot-transport">Troubleshoot transport methodically</h2>

1. Confirm the intended protocol, destination address, and destination port.
2. Verify routing and local gateway resolution toward the destination.
3. Inspect whether the expected TCP or UDP listener exists on the destination.
4. Check local, network, and remote firewall or security policy.
5. Capture both directions and separate RST, ICMP evidence, and silence.
6. Investigate the return path independently from the forward path.
7. After transport succeeds, test the application's own request and response.

<InterviewScenario title="UDP request receives no reply">Explain why UDP silence does not prove a closed port. Identify application logging, socket state, capture evidence, ICMP errors, policy, and a controlled known-good comparison.</InterviewScenario>
