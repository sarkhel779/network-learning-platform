<h2 id="read-a-basic-routing-table">Read a basic routing table</h2>

A useful beginner view has four fields. Read the destination and prefix first, then the next hop
and interface. The default route is a fallback; it does not automatically beat a more-specific route.

Windows exposes related read-only evidence with `route print`. Linux commonly uses `ip route`.
Field names and formatting vary, so normalize what you see into the four columns above before
drawing a conclusion. These examples are static; the site does not inspect your device.

```text
Windows route print: 0.0.0.0  0.0.0.0  192.0.2.1  192.0.2.10
Linux ip route: default via 192.0.2.1 dev eth0
```

<h2 id="diagnose-gateway-boundary-problems">Diagnose gateway and boundary problems</h2>

Use one evidence-first sequence:

1. Define the source, destination, direction, and exact symptom.
2. Confirm the host address and configured prefix instead of assuming `/24`.
3. Decide whether the destination should be on-link or remote.
4. Find the most-specific matching route and outgoing interface.
5. Confirm that the selected gateway is reachable on that local interface.
6. Test the local next hop separately from the remote destination.
7. If the gateway is reachable, inspect the next router or return path with appropriately scoped evidence.

No matching route is a host routing failure. A matching route with an unreachable gateway is a
local next-hop problem. A packet that reaches the gateway but meets no onward route is a router-side
forwarding problem. These symptoms need different fixes.

<InterviewScenario prompt="A host can reach its default gateway but cannot reach a remote server. How would you narrow the fault domain?">
First verify the destination and selected route, then separate forward-path evidence from the return
path. Since the gateway is reachable, do not begin by changing the host's ARP cache. Inspect whether
the gateway has an onward route, whether later hops respond, and whether the return path is valid.
</InterviewScenario>

Remember: apply the configured prefix, select the most-specific route, resolve only the local next
hop, and distinguish end-to-end IP addressing from hop-by-hop Layer 2 framing.
