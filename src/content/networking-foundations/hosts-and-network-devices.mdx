This lesson answers a different question from **How Networks Communicate**. The first lesson
followed the data; this lesson identifies the devices on that path, the evidence each device
uses, and the point where you would investigate when communication fails.

<h2 id="what-is-a-host">What is a host?</h2>

A **host** is an endpoint that originates, receives, or processes network data. A laptop,
desktop, server, printer, phone, and IP camera can all be hosts. Applications run on hosts;
switches and routers help their traffic reach other hosts.

The words *client* and *server* describe roles, not permanent device types. A laptop may be a
client while requesting a web page and a server while sharing a file. The source and
destination can also reverse when the reply travels back.

Before sending IPv4 traffic, a host makes one crucial decision:

1. Compare the destination IP address with its own address and subnet mask.
2. If the destination is local, send toward that host's MAC address.
3. If the destination is remote, send toward the default gateway's MAC address.

ARP can supply the required local-link MAC address. ARP is introduced here only as evidence
of that decision; a later lesson will examine ARP and MAC learning in depth.

<h2 id="connecting-devices">Devices that connect hosts</h2>

An **intermediary device** connects endpoints or network segments. It forwards, filters, or
translates traffic; it is not normally the application endpoint for the user's conversation.

| Device | Primary evidence | Main decision | What changes or stays the same |
| --- | --- | --- | --- |
| Layer 2 switch | Destination MAC address and MAC table | Which LAN port should receive the frame? | Forwards the frame; does not route the IP packet |
| Wireless access point | Wi-Fi association plus link-layer addressing | Which wired or wireless side should carry the frame? | Bridges wireless and wired LAN traffic |
| Router/default gateway | Destination IP address and routing table | Which next network or next hop should receive the packet? | Removes the incoming frame and builds a new frame for the next link |
| Firewall | Session state, zones, addresses, ports, applications, and policy | Is this traffic permitted across the boundary? | May allow, deny, log, or translate traffic |
| Server | Destination address and listening service | Which local application should process the request? | Receives the request and can originate the return traffic |

A home device may combine an access point, switch, router, firewall, and DHCP service in one
box. The functions remain distinct even when the hardware is shared. This lesson introduces
the firewall boundary briefly; policy design and Palo Alto behavior belong in the separate
firewall module.

<h2 id="compare-journeys">Compare packet journeys</h2>

Change the journey above and watch which devices become relevant.

- **Wired to local:** host → switch → local server, then the reverse path.
- **Wireless to local:** laptop → access point → switch → local server, then back through the switch and access point.
- **Wired to remote:** host → switch → gateway → firewall → remote server, with a routed return.
- **Wireless to remote:** laptop → access point → switch → gateway → firewall → remote server, followed by the complete return journey.

The switch is still important in a remote journey, but it does not decide the end-to-end IP
route. The access point does not become the laptop's IP gateway merely because it provides the
wireless connection. At every routed hop, the link-layer frame can change while the source and
destination IP addresses normally continue to identify the communicating hosts.

<InterviewScenario prompt="A user can reach local devices, but remote destinations fail after someone changed the default gateway. Where do you start?">
  Confirm the host's IP address, mask, and configured gateway with `ipconfig /all`. Compare the
  destination with the local subnet, inspect `route print`, and test whether the configured
  gateway is locally reachable. Local communication can still work because it does not need
  the gateway; remote communication exposes the incorrect next-hop decision.
</InterviewScenario>

<InterviewScenario prompt="Several wired hosts lose connectivity when one access switch becomes unavailable. What does that tell you?">
  Start at the shared switch, its power and uplinks, and the affected access ports. A failed
  Layer 2 path can prevent ARP, gateway reachability, and local server access at the same time.
  Separate the host-specific checks from evidence common to every affected host.
</InterviewScenario>

<InterviewScenario prompt="A wireless laptop is disconnected from its access point while wired users still work. Which boundary is most likely failing?">
  Investigate the wireless association first: radio availability, SSID, authentication, signal,
  and whether the client obtained valid network settings. The working wired users make the
  upstream switch, gateway, and server less likely as the first failure point.
</InterviewScenario>

<h2 id="windows-checks">Windows checks</h2>

Run commands in Command Prompt or PowerShell and treat the output as evidence, not as a pass or
fail badge.

```text
ipconfig /all
```

Check the active adapter, IPv4 address, subnet mask, default gateway, DHCP state, DNS servers,
and physical address. A disconnected adapter or a self-assigned `169.254.0.0/16` address changes
the investigation immediately.

```text
arp -a
```

Look for the local target's address on a local journey or the gateway's address on a remote
journey. An empty entry is not automatically a fault; it can mean the host has not communicated
recently. Generate relevant traffic and observe whether resolution succeeds.

```text
route print
```

Find the route that best matches the destination. For a remote destination, confirm that the
default route points to a gateway reachable through the expected interface. More-specific
routes take precedence over the default route.

<InterviewScenario prompt="The ARP cache is empty before a ping. Is that proof of a network fault?">
  No. The entry may have expired or the host may not have needed it yet. Start a capture, ping
  the relevant local target or gateway, and look for an ARP request and reply. Repeated requests
  without a reply are stronger evidence of a local-link, VLAN, target, or addressing problem.
</InterviewScenario>

<h2 id="wireshark-checks">Wireshark checks</h2>

Capture on the host's active interface and begin with narrow display filters:

| Goal | Display filter | Evidence to compare |
| --- | --- | --- |
| Find address resolution | `arp` | Request, reply, requested IPv4 address, learned MAC address |
| Follow a ping | `icmp` | Echo request and reply, source and destination IP |
| Focus on the remote server | `ip.addr == 203.0.113.50` | Both outbound and return packets |
| Focus on one Ethernet endpoint | `eth.addr == 02:00:00:00:10:01` | Frames visible on this capture link |
| Find TCP conversations | `tcp` | Endpoints, ports, flags, retransmissions, and replies |

<WiresharkCheck
  filter="arp or icmp or ip.addr == 203.0.113.50"
  fields={["eth.src", "eth.dst", "arp.opcode", "ip.src", "ip.dst", "icmp.type"]}
  normalEvidence="A local IPv4 journey commonly shows ARP followed by request and reply traffic. A remote journey resolves the gateway on the first link, while the IP destination continues to identify the remote server."
  exercise="Choose one journey, predict the next-hop MAC address, then compare the request and return packets. Use tcp separately when testing a TCP-based service."
/>

Your capture point limits what you can see. A capture on the source host shows its local link;
it cannot reveal every Ethernet frame rebuilt beyond a router. To compare routed-link frames,
you need captures or telemetry at those other points. Never infer an entire path from one
capture without stating that limitation.

<InterviewScenario prompt="Traffic reaches a firewall boundary but no reply returns. How would you explain the next checks without turning this into a firewall deep dive?">
  Verify that the request arrived on the expected interface and that the source, destination,
  service, and session evidence match the intended flow. Then check whether policy permits it,
  whether translation is expected, and whether a route exists in both directions. A firewall
  deny is one possibility; an asymmetric or missing return route can look similar from the host.
</InterviewScenario>

1. Classify the source and destination hosts and each intermediary function.
2. Decide whether the server is local or remote from the failing host.

4. Identify the last confirmed working boundary using host commands and packet captures.
5. Trace the return path instead of stopping when the request leaves the source.
6. State what your capture location cannot prove.

<h2 id="summary">Summary</h2>

| Question | Practical answer |
| --- | --- |
| Who creates or consumes the data? | A host, acting as a source, destination, client, or server |
| Who forwards within the LAN? | A switch or access point using link-layer information |
| Who connects different IP networks? | A router/default gateway using its routing table |
| Who enforces the security boundary? | A firewall using policy and session context |
| What does the host choose first? | Local destination or remote next hop |
| What must troubleshooting include? | The outbound path, return path, evidence, and capture limitations |

You can now identify what each device contributes to a packet journey and choose a sensible
first troubleshooting boundary. The next lesson maps these functions to the OSI and TCP/IP
models; later modules will deepen ARP, switching, routing, firewall behavior, and Palo Alto
basics without overloading this foundation.
