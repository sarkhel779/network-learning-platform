<h2 id="diagnose-local-switching-symptoms">Diagnose local switching symptoms</h2>

Use an evidence-first sequence: define the affected hosts and direction, verify physical link
and port state, identify ingress and expected egress ports, read the source and destination MAC
addresses, inspect the forwarding table and entry freshness, then change one condition and retest.

### MAC learned on an unexpected port

Confirm the host identity and physical path before changing anything. A source entry on an
unexpected port may show that the host moved, that another device is forwarding its frames,
or that the assumed cabling record is wrong. Record the newest source frame and ingress port;
the table entry alone does not prove a loop.

### Missing or aged destination entry

A missing entry makes a unicast destination unknown, so temporary flooding is expected. Check
whether a frame from that destination refreshes the table. Absence is not proof that the switch
is broken, and the aging interval depends on the implementation.

### Broadcast seen on several ports

An Ethernet broadcast is meant to reach eligible ports in the same Layer 2 domain except its
ingress port. Seeing it on several ports is not automatically a loop. First verify its broadcast
destination and whether repeated copies continue beyond one expected forwarding event.

### Same-port filtering

When a classic bridge learns both source and destination behind one segment, it filters the
frame instead of sending it to other segments. Confirm the ingress port and destination entry;
zero egress ports can be the correct decision rather than a loss.

### Host moved between switch ports

A foundational moved-host case records: **Host moved from port 2 to port 4**. Send or observe a
new frame sourced by that host and confirm that source learning refreshes the entry to port 4.
The old entry can explain misdelivery, but IP settings and application state still require
separate evidence.

### Physical-link failure

If a required link is down, editing or clearing the forwarding table cannot restore the signal.
Verify power, cable or radio path, interface state, and link evidence at both ends first. Repair
the physical condition, then observe new source learning and repeat the original traffic test.

<h2 id="knowledge-check-summary">Knowledge check and summary</h2>

Account practice will check whether the learner can distinguish known-unicast forwarding,
same-port filtering, unknown-unicast flooding, and broadcast flooding without confusing a
switching decision with routing or application reachability.

Remember the order: learn the source on ingress, classify and look up the destination, then
forward, filter, or flood. A populated forwarding table proves only learned Layer 2 locations;
it does not prove correct IP configuration or a working destination application.
