<h2 id="inspect-security-evidence">Inspect security evidence</h2>

`openssl s_client -connect host:443` opens a raw TLS connection and prints the negotiated protocol version, cipher suite, and the full certificate chain the server presented — the fastest way to see a real handshake's outcome without a packet capture. Reading the chain from the leaf certificate up to the root shows exactly which certificate authorities a client is being asked to trust.

<WiresharkCheck displayFilter="tls.handshake">Capture a browser connecting to an HTTPS site. Identify the Client Hello (the cipher suites and TLS version the client offers), the Server Hello (what the server actually selected), and the Certificate message carrying the server's public key and identity — all sent before any application data is encrypted.</WiresharkCheck>

<h2 id="guided-cryptography-practice">Guided cryptography practice</h2>

Work through why hybrid encryption is universal, not just common. Alice wants to send Bob a 50 MB file confidentially. Encrypting the whole file directly with an asymmetric algorithm like RSA would be thousands of times slower than symmetric encryption and is not what any real protocol does. Instead: Alice generates a random symmetric session key, encrypts the 50 MB file with that key using AES (fast, regardless of size), and encrypts only the small session key itself with Bob's public RSA key (or, as in TLS 1.3, both sides derive the session key together via a Diffie-Hellman exchange, so no key ever needs to be encrypted and sent at all). Bob decrypts the session key with his private key, then uses it to decrypt the file.

<InterviewScenario title="Why not just use a longer RSA key everywhere instead of hybrid encryption?">A candidate suggests that since asymmetric cryptography is "more secure," using it for everything — not just the session key — would be the safer design. Explain why this reasoning is wrong: it conflates key length with practical throughput, and a sufficiently long symmetric key (AES-256) is already considered infeasible to brute-force, so there is no realized security benefit to abandoning the hybrid approach, only a catastrophic performance cost.</InterviewScenario>

<h2 id="troubleshoot-security-basics">Troubleshoot security basics</h2>

1. Check for clock skew first: certificate validity windows and several handshake protocols depend on roughly synchronized time (NTP), and a large clock skew produces confusing "not yet valid" or "expired" certificate errors on a certificate that is actually fine.
2. Confirm the client and server share at least one common cipher suite or key-exchange algorithm — a "handshake failure" with no application-layer error usually means negotiation failed, not that credentials were wrong.
3. Walk the certificate chain from leaf to root and confirm every intermediate certificate is present — a missing intermediate is one of the most common causes of "untrusted certificate" errors on an otherwise correctly issued certificate.
4. Check whether a deprecated or weak algorithm (RC4, DES, SSLv3) is still enabled for legacy compatibility, since its presence can itself be the finding during a security review even if nothing is actively "broken."
5. Distinguish "connection refused" (a network- or firewall-layer problem, before any cryptography is involved) from "handshake failure" (the connection reached the service, but cryptographic negotiation itself failed) — they point to completely different layers.
6. Consider whether a middlebox (a TLS-inspecting proxy or firewall) is intercepting the connection, which replaces the real server's certificate with one of its own and breaks certificate validation unless the proxy's certificate was explicitly trusted.

<InterviewScenario title="A browser reports an untrusted certificate for a server you believe is configured correctly">List the most likely causes in the order you'd check them: a missing intermediate certificate in the chain served by the server, significant clock skew on the client, a hostname that doesn't match any name on the certificate, and a self-signed certificate the client was never told to trust.</InterviewScenario>
