<h2 id="inspect-ssh-evidence">Inspect SSH evidence</h2>

`ssh -v user@host` prints the full handshake to the terminal: the negotiated key exchange and host-key algorithms, the host-key fingerprint being checked against `known_hosts`, and which authentication methods were offered and accepted. `ssh-keygen -lf ~/.ssh/known_hosts` lists the fingerprints SSH has already trusted for past connections, which is exactly what a client compares a server's host key against on every new connection.

<WiresharkCheck displayFilter="ssh">Capture an SSH connection being established. You'll see the initial cleartext version banner and the KEXINIT algorithm negotiation — but almost everything after the key exchange, including authentication and all session data, is encrypted and shows up as opaque SSH binary packets, not readable content.</WiresharkCheck>

<h2 id="guided-ssh-key-practice">Guided SSH key practice</h2>

Work through why public-key authentication specifically defeats phishing, not just brute-forcing. With password authentication, an attacker who tricks a user into typing their password into a fake prompt now has the actual secret, and can use it to authenticate anywhere that password is valid. With public-key authentication, the server sends a *different* random challenge on every single connection attempt, and the client's response (a signature over that challenge) is only valid for that one exchange — capturing a signed response from a previous login doesn't let an attacker authenticate again, because the next challenge will be different. There is simply no reusable secret for a phishing page to capture.

<InterviewScenario title="An attacker phishes a user's SSH password — would public-key authentication have prevented this?">Explain precisely why: with public-key authentication there is no password for a fake login page to capture, and even capturing a legitimate signed response from a real session doesn't help an attacker, since the private key itself never leaves the user's machine and each authentication challenge is different.</InterviewScenario>

<h2 id="troubleshoot-ssh">Troubleshoot SSH</h2>

1. Check private key file permissions first: SSH clients refuse to use a private key file that is readable by other users on the system (commonly reported as "Permissions 0644 for 'id_rsa' are too open").
2. A "WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED" message means the server's host key no longer matches what's stored in `known_hosts` — treat this as a possible man-in-the-middle until you've verified the change out-of-band (for example, confirming with the server's administrator that it was rebuilt or re-keyed).
3. If the wrong identity is offered during authentication, confirm which private key the client is actually using (`-i` to specify one explicitly, or check what's loaded in `ssh-agent`) rather than assuming the default key is the one on the server's `authorized_keys`.
4. Rule out a network-layer problem (firewall blocking TCP 22, or the server listening on a nonstandard port) before assuming the issue is cryptographic — a connection that never completes the TCP handshake isn't an SSH problem at all.
5. An "no matching key exchange method found" (or similar algorithm-negotiation) error means the client and server share no common algorithm — often a hardened modern client refusing to use a legacy server's outdated options, or vice versa.
6. On the server, confirm `authorized_keys` and the `.ssh` directory have the expected ownership and restrictive permissions — SSH servers, like clients, often silently ignore a key file whose permissions are too permissive.

<InterviewScenario title="A user reports the host-key warning and wants to just delete the known_hosts entry and reconnect">Walk through how you'd verify whether this is a legitimate change (a server rebuild, a planned host-key rotation) or an active attack before telling them to proceed — and why simply deleting the warning without investigating defeats the entire purpose of trust-on-first-use.</InterviewScenario>
