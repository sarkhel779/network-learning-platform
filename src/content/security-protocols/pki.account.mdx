<h2 id="inspect-pki-evidence">Inspect PKI evidence</h2>

`openssl x509 -in cert.pem -text -noout` prints every field of a certificate in human-readable form — subject, issuer, validity dates, SAN entries, and the signature algorithm. `openssl s_client -connect host:443 -showcerts` dumps the entire chain a server actually presents, which is the fastest way to confirm whether a missing intermediate is the problem. `openssl verify -CAfile root.pem -untrusted intermediate.pem leaf.pem` manually walks and verifies a chain against a specific trusted root, which is useful for testing a chain independently of any particular browser's trust store.

<WiresharkCheck displayFilter="tls.handshake.certificate">Capture a TLS handshake and inspect the Certificate message. Confirm whether the server sent just the leaf certificate or the leaf plus its intermediate — a server that only sends the leaf is relying on every client already having the intermediate cached, which is not a safe assumption.</WiresharkCheck>

<h2 id="guided-chain-of-trust-practice">Guided chain-of-trust practice</h2>

Work through what actually happens if an intermediate CA's private key is compromised, and why the root doesn't need to be replaced as a result. The root CA's key itself was never exposed, so the root remains trustworthy — but every certificate that compromised intermediate ever issued is now suspect, because an attacker holding that key could have issued fraudulent certificates for any hostname. The fix is to revoke that one intermediate (added to a CRL, or simply removed from distribution) and have all genuinely legitimate certificates it issued re-issued under a new, uncompromised intermediate. This is exactly the isolation intermediates are designed to provide: a compromise is contained to what that one intermediate touched, rather than invalidating the entire chain of trust back to the root.

<InterviewScenario title="If an intermediate CA is compromised, does the root CA need to be replaced too?">Explain why the answer is no: the root's own private key was never exposed, so distrusting or replacing it would be an overreaction. Revoking the compromised intermediate and re-issuing its legitimate certificates under a new one fully contains the damage — which is the entire reason the chain uses intermediates instead of having the root sign every certificate directly.</InterviewScenario>

<h2 id="troubleshoot-pki">Troubleshoot PKI</h2>

1. Check for a missing intermediate certificate first: a server that only serves its leaf certificate forces every client to already have the correct intermediate cached, which many don't — this is the single most common cause of "untrusted certificate" errors on a certificate that was actually issued correctly.
2. Confirm the certificate's actual not-after date rather than assuming it hasn't expired — an expired certificate produces the same category of browser warning as an untrusted chain, but the fix is entirely different (renewal, not a missing intermediate).
3. Check the SAN extension against the exact hostname being requested — a certificate can be perfectly valid and trusted and still fail for the wrong hostname, such as a certificate issued for `www.example.com` being presented for `example.com` without both names listed.
4. Distinguish a genuinely self-signed, untrusted certificate (no path to any trusted root at all) from a broken chain (a path exists but an intermediate is missing) — the first requires explicitly trusting that certificate, the second just requires the server to send its full chain.
5. Rule out client clock skew: certificate validity checks compare absolute timestamps, so a sufficiently wrong client clock can reject a perfectly valid certificate (or fail to reject an actually-expired one).
6. Remember that revocation checks commonly **soft-fail**: if a client can't reach an OCSP responder, many implementations proceed as though the certificate were valid rather than blocking the connection — a known trust gap, not a malfunction.

<InterviewScenario title="Why do many clients 'soft-fail' when an OCSP check can't complete, instead of blocking the connection?">Explain the tradeoff: hard-failing would break connectivity every time a CA's OCSP responder is slow, overloaded, or unreachable — which happens often enough in practice that most browsers prioritize availability over catching every revoked-but-still-live certificate. This exact gap is why OCSP stapling and short-lived, frequently renewed certificates matter — they shrink the window this soft-fail behavior can be exploited in.</InterviewScenario>
